Source control for monorepos at agent scale

Commits, rebases and history run on the server. Clients stay thin, CI reads files without cloning, and sixteen agents can land on one branch at once without a single retry.

Install Sapwood Read the source

Open source under Apache-2.0. Written in Rust. Runs on a laptop with SQLite or on Postgres and S3 behind regional caches.

Measured on git's own history

Same repository, same machine, both systems local. git/git: 82,443 commits and 4,857 files. Apple M4, release builds, median of five runs. Reproduce with bench/run.sh.

Server storage after sapwood compact is 369 MB against git's 333 MB pack (1.1x); before compaction it is 4.6 GB. A full Sapwood workspace keeps 380 KB of metadata where git keeps 334 MB of history.

Why it stays fast as history grows

The largest monorepos moved history and commit creation to the server. Sapwood brings that model to everyone, as open source.

The server builds commits

Your client sends the list of files you changed. The server updates the tree, so the cost of a commit follows the size of your change, not the size of the repository.

Landing needs no lock

When main has moved, the server rebases your change and moves the branch with one compare-and-swap. Changes that touch different files all land; there is no merge queue to wait in.

Caches are never stale

Every object is named by the hash of its content, so a cached copy is correct forever. Regional caches and per-machine daemons answer the same requests the server does.

Built for agents to use directly

Sapwood ships a Model Context Protocol server. Any MCP client can read files at any revision, commit, and land, without shelling out or parsing terminal output.

Fits how your company already works

Adopt it one team at a time. Nobody has to give up git on day one.

  • Plain git keeps workinggit clone sapwood::https://…, push and pull through a built-in remote helper. A push to a branch that moved is rebased by the server instead of rejected.
  • Single sign-onOkta, Entra ID, Google, Auth0 or Keycloak tokens through OpenID Connect, next to tokens for CI.
  • Folder-level permissionsDecide who can read and who can write each directory. People with partial access get a checkout, history and search that contain only what they may see.
  • Large filesFiles are split into content-defined chunks, so editing a large asset uploads only what changed. A 1 GiB file commits in under 200 MB of memory.
  • Build machines start warmA node daemon can preload a branch and follow it as it moves. On git/git, the first checkout on a fresh machine went from 4.2 s to 0.35 s.
  • Mount instead of cloneOn Linux, sap mount shows a whole revision as a read-only folder. Files download the first time something reads them, and only the parts that are read.

Try it on your own repository

Import keeps your full history and is safe to re-run; new git commits fast-forward the branch. Export writes it back to git with identical trees, so you are never locked in.

For the full topology with Postgres, S3-compatible storage, a regional cache and a node daemon, run docker compose up from the repository.

# Install (macOS, Linux)
curl -fsSL https://raw.githubusercontent.com/kabirnarang39/sapwood/main/install.sh | sh

# Start a server and import your history
sapwood server --listen 127.0.0.1:7420 &
sap import-git ~/code/my-repo --server http://127.0.0.1:7420

# Work
sap clone http://127.0.0.1:7420 work && cd work
sap commit -m "First change" && sap land

Coming from git

The verbs you know still work: sap push lands and sap pull syncs. Or keep using git itself: git clone sapwood::http://host:7420 works, and a push to a branch that moved is rebased by the server instead of rejected.

Where git is still the better tool

Sapwood makes a trade on purpose. These are the costs.

  • Working offlineHistory, commits and landing need the server. That is how clients stay small.
  • The ecosystemEvery tool speaks git. Lossless import and export keep the door open both ways.
  • SubmodulesSubmodules are not supported; vendor the code or use a package manager.
  • Merged side branches in historyLog and blame show what landed on the branch, not every merged-in commit.
