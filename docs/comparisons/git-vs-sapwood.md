# git vs Sapwood

Both tools are excellent at different things. This page says where each one wins, with
measurements you can reproduce (`bench/run.sh`).

### Methodology

* Corpus: [git/git](https://github.com/git/git) (82,443 commits, ~4,900 files): real,
  public, and with 20 years of history.
* git is served over `file://` (the real pack protocol, no network latency) with
  `uploadpack.allowFilter` enabled so partial clone is available to git.
* Sapwood runs as a release-build server on SQLite, over loopback gRPC.
* For each scenario git gets its best practice: partial clone + sparse checkout for sparse
  clones, `--depth 1 --filter=blob:none` for single-file CI reads, `--first-parent` for
  log/blame (Sapwood's history is first-parent, i.e. what landed).
* [hyperfine](https://github.com/sharkdp/hyperfine) median of 5 runs after a warm-up run.

## Where Sapwood wins, and why

* **Clones**: Sapwood transfers one tree's worth of objects, never history. The gap
  grows with history length; at monorepo scale git's full clone is the dominant CI cost.
* **CI reads**: `sap cat main path` is one RPC. git needs at least a shallow, filtered clone.
* **Publishing under contention**: git's push loses every race and must fetch + rebase +
  retry on the client. Sapwood rebases on the server and moves the ref by compare-and-swap,
  so concurrent non-conflicting lands all succeed without client retries.
* **Thin clients**: a Sapwood workspace's metadata is an index, not a copy of history.

## Where git wins

* **Offline work**: git has everything locally. Sapwood needs the server for history,
  commits and landing (by design).
* **Server storage**: git's delta-compressed packs are several times smaller than
  Sapwood's per-object zstd storage (see footprint table). Delta storage is on the roadmap.
* **Path-filtered history on huge histories**: git can use commit-graph Bloom filters;
  Sapwood v1 walks first-parent history server-side (bounded). A derived path index is on
  the roadmap.
* **Ecosystem**: every tool speaks git. Sapwood offers lossless `import-git` / `export-git`
  so you are never locked in.

## Semantics differences

| | git | Sapwood |
|---|---|---|
| Commit | local snapshot | server-side changeset (list of changed files vs first parent) |
| Staging area | yes | no; `sap commit [PATHS]` commits all or a subset |
| Branches | cheap, everywhere | supported (`sap checkout -b`), but `main` is the default lane; refs are global state |
| History shown by log/blame | full DAG | first-parent (what landed) |
| Submodules | yes | not supported (skipped on import) |
| Hash | SHA-1 (SHA-256 opt-in) | BLAKE3 |
